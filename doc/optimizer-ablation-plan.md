# 优化器性能归因方案（v1，待评审）

> 目标不是"把优化器改快"，而是**查清现在慢在哪、每一处改动各自贡献了多少时间与多少质量，
> 然后只保留划算的那几处**。默认行为在任何阶段都不改变。

---

## 0. 为什么改成"一个一个加"

上一轮我做的事是：一次性把 projected L-BFGS 的所有正确性修正 + two-loop 闭式化 + 掩码/同步
精简全部落地，然后才测量。测量显示优化器**内部** ATen op 从 850→373、CPU 单迭代 1.97×——
但真实拟合里看不出速度变化。

这说明我的模型错了：**我把"op 数"当成了"时间"。** 如果一次迭代里 `getNLL+backward` 占
50 ms、优化器 housekeeping 占 1 ms，那 housekeeping 就算快 3 倍，总时间也只动 ~1.3%。

正确顺序是：**先归因（measure）→ 找到最大项 → 只改那一项 → 再测 → 决定保留或回退。**

同理，如果某一个"正确性修正"其实对质量没贡献（比如在你们的 config 里参数根本不会贴边），
它也应当被回退——**每多一行代码都是一个长期的维护与理解成本**。

## 1. 先确认三件事（零代码改动，约 10 分钟）

### 1.1 你现在的"慢"具体慢在哪个环节

用**你真实的那条命令**跑一次，只需要一次，记录下面 6 个数（缺一不可）：

| 字段 | 含义 | 从哪里拿 |
|---|---|---|
| `t_init` | 振幅初始化耗时（读 phsp/data + 建振幅） | 现有打印 `振幅初始化耗时` |
| `n_evals` | 每次 run 的目标函数求值次数 | 现有 `迭代次数`（= 求值数） |
| `t_fit` | 每次 run 优化耗时 | 现有 `耗时` |
| `t_hess` | 每次 run 末尾 Hessian 耗时 | 现有 `Hessian` |
| `t_polish` / `polish_steps` | 抛光耗时与步数 | 需补一行计时（P0 插桩） |
| `optimizer_status` | **走的是哪条路径** | 现有 `优化器状态`：`projected-gradient/max-iter/...` = 新路径；`lbfgs` = **老路径** |

> ⚠ 第一种可能的解释：如果 `optimizer_status = lbfgs`，说明那次跑的是 `--optimizer lbfgs`
> 或 `FIT_OPTIMIZER=lbfgs`，我的 two-loop 改动**一行都没生效**，速度当然不变。

### 1.2 对照基线到底是哪一版

"慢了许多"必须有一个明确的参照物：

- 参照物是 `ctpwa 969ad28`（Sep 7，torch LBFGS + clamp + 40 步 polish）？
- 还是 `Jpsi2KKeta/solve1/fit.py`（6 月版，**没有 polish**）？
- 还是 `/home/whitewash/pwa` 仓库里 `HEAD:Jpsi2KKeta/solve2/fit.py`？

并且要有那一次跑的 wall time / NLL。**没有基线数字就无法判断"变慢"是 1.5× 还是 20×。**

### 1.3 单次求值的真实成本拆分

在真实 config 上量：一次 `getNLL`、一次 `backward` 各多少 ms（用现有分析对象写个 10 行脚本，
不需要改 fit.py）。这决定"优化器 housekeeping 最多能占总时间多少"——也就是我上一轮改动
的理论天花板。

## 2. 需要的唯一代码改动：开关矩阵（默认全部 = 当前行为）

把所有历史改动变成 env 开关，**每个开关只翻一个变量**，并在输出里回显本次用的开关组合
（结果自描述）。不新增任何物理内容。

| 开关 | 取值 | 作用 |
|---|---|---|
| `FIT_OPT_OPTIMIZER` | `projected` / `lbfgs` | 新投影 L-BFGS vs 老 torch LBFGS（已存在） |
| `FIT_OPT_LEGACY_SIGN` | `0` / `1` | legacy 路径恢复**旧的（写反的）**梯度投影符号，用于精确复现历史行为 |
| `FIT_OPT_HONEST` | `1` / `0` | 投影路径也用 clamp+清零梯度（隔离"真实梯度"这一项） |
| `FIT_OPT_M` | 5 / 15 / 50 / 100 | 曲率历史长度（已存在） |
| `FIT_OPT_TWOLOOP` | `batched` / `legacy` | 闭式 two-loop vs 逐 `torch.dot`（**用来验证我上一轮改动到底有没有用**） |
| `FIT_OPT_KKT_EVERY` | 1 / 5 / 10 | 每 k 轮才做一次 KKT 检查（省 sync） |
| `FIT_OPT_POLISH` | `1` / `0` | 开/关抛光（CLI 已有 `--no-polish`） |
| `FIT_OPT_POLISH_MODE` | `new` / `old` | 新阻尼牛顿 vs 旧 40 步版本 |
| `FIT_OPT_POLISH_STEPS` | 40 / 200 | 抛光步数上限 |
| `FIT_OPT_WARM_RES` | `1` / `0` | warm start 是否带共振态参数 |
| `FIT_OPT_PROF` | `0` / `1` | 打印/落盘 eval vs housekeeping 耗时拆分（已存在） |

**阶段 2.5（可选）**：`FIT_OPT_TWOLOOP=legacy` 若证明我上一轮改动无收益，直接回退那段
改动（保持 `git diff` 最小）。

## 3. 实验阶梯（每次只翻一个开关）

固定：同一 config、同一 `--runs`、同一 `--niter`、同一种子序列（run i = seed 42+i）、
同一台机器、无其他 GPU 任务。每个配置**重复 3 次**取中位数。

| 编号 | 配置 | 回答什么问题 |
|---|---|---|
| **L0** | 当前 projected（全开） | 基线：时间与质量 |
| **L1** | L0 + `--no-polish` | 抛光占多少时间、多少质量（最可能的"罪魁"） |
| **L2** | L1 + `--niter 200` | 迭代预算与时间/质量的关系（找拐点，不是越少越好） |
| **L3** | `--optimizer lbfgs`（可选 + 旧符号） | 老的快，是快在"真的收敛快"还是"伪收敛提前退出" |
| **L4** | L0 + `FIT_OPT_HONEST=0` | "真实梯度"这一项贡献多少时间、多少质量 |
| **L5** | L0 + `FIT_OPT_M ∈ {5,15,50,100}` | m 的真实效应（我上轮预测它无收益，需验证） |
| **L6** | L0 + `FIT_OPT_TWOLOOP=legacy` | **我上一轮改动的真实价值**（若 ≈0 → 回退） |
| **L7** | L0 ± `FIT_OPT_WARM_RES` | warm start 带 θ 的收益/风险 |
| **L8** | L0 + `FIT_OPT_KKT_EVERY=5` | 省 sync 是否值得（会轻微改变停机点） |

产出：`attribution.md` —— 一行一个实验，列 `wall / evals / t_fit / t_hess / t_polish /
final_nll / status / pd / n_pinned`。

## 5. 判定规则（先定规矩，再看结果）

### 5.1 先标定噪声（否则一切结论都不成立）

用 L0 跑 **10 个不同种子**，得到：
- 终值 NLL 的离散度（mean / std / min / max）；
- wall time 的离散度。

你们的 `chic2ppeta` 记录里 10 个 run 的 NLL 分布横跨 ~5900，所以**先知道噪声，
再谈"改进"**。判定阈值：

- **质量显著**：ΔNLL > 3（约 2 个自由参数）才叫真改进；有 `dataEvents` 时用 BIC，
  ΔNLL > ln(N_data) ≈ 12 才叫显著。
- **时间显著**：3 次重复的中位数改善 > 10% 才算真（GPU 时钟/调度抖动在 5% 量级）。

### 5.2 保留/回退规则

| 情况 | 决定 |
|---|---|
| 时间显著↓ 且 质量不显著变差（ΔNLL < 3） | **保留** |
| 质量显著↑ 且 时间代价在预算内 | **保留**，并折算"每 NLL / 每小时" |
| 质量显著↑ 但 时间代价超预算 | 只在最终定稿时用，探索阶段关闭 |
| 时间/质量都不显著 | **回退**（包括我上一轮的 two-loop 改动） |

### 5.3 "解决"的定义（提前写死，避免事后挪门槛）

1. 质量前提：终值 NLL 距已知最好 ≤ 3（或 BIC 阈值）；Hessian 在非活跃子空间正定；
   被 `free_range` 钉住的自由参数数 = 0（这是新版买到的正确性）；
2. 时间目标：在满足 1 的前提下，总 wall time（不含 `t_init`）≤ 老基线的 1.2×，
   或"单位时间获得的质量"优于老基线；
3. 达到 2 之后**停止加东西**，把当前开关组合冻结成默认值。

## 6. 阶段与产出

| 阶段 | 内容 | 产出 | 估计 |
|---|---|---|---|
| P0 | 三件确认 + 插桩（零行为变化） | `timing.jsonl`、单次 eval 成本拆分 | 半天 |
| P1 | L0–L8 阶梯 | `attribution.md`：每个改动 = 多少秒 / 多少 NLL | 1–2 天 |
| P2 | 只针对最大项做 1–2 个候选修复，单候选 A/B | 候选对比表 + 显著性判定 | 取决于 P1 |
| P3 | 冻结 + 文档化（含"为什么不做 X"） | 默认值 + 一份说明 | 半天 |

**P2 的候选（先列出来，但必须等 P1 数据才决定做哪个）**：
- 抛光预算自适应（按 `|pg|` 与 Hessian 成本决定是否继续，而不是固定 200 步）；
- Hessian 复用/降阶（沿最平方向做低维子空间牛顿）；
- KKT 检查间隔 + 批量线搜索试探（把多次试点的 f 合并成一次批量化求值——需要 ctpwa 侧支持）；
- 优化器整步 CUDA kernel 化（P3 级工作量，只在 housekeeping 被证明是大头时才做）。

## 7. 我需要的东西

1. **GPU 使用权限**：一次只跑一个 fit；跑完立即释放；用后台 job + `nvidia-smi` 监控；
   不与其他任务抢显存（你们卡是 8.5 GiB，需确认 fit 的显存占用）。
2. **实验目录**：建议把 `solve2` 复制成一个专用 `bench/` 目录（独立 `results_*`），
   **绝不覆盖现有 `results/`**。
3. **真实命令 + 对照基线**（1.1 / 1.2 的 6 个数字与那一次的时间）。
4. **时间预算**：单次实验可接受到什么量级（分钟级 / 半小时级 / 小时级），决定阶梯怎么裁剪。
5. **确认可以加第 2 节那组 env 开关**（默认全关，生产行为不变）。

## 8. 风险与回退

- 所有实验写独立 `--output-dir`，不触碰现有结果；开关默认 = 当前行为。
- 任何被证明无收益的改动（含我上一轮的）**直接回退**，保持 diff 最小。
- 若 P1 证明 `getNLL/backward` 占了 90%+，则结论是"优化器已不是瓶颈"，
  应当停止在优化器上投入，转去查求值本身（振幅重算、精度模式、Hessian 阶段）。
